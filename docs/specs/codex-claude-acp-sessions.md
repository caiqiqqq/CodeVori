# Built-in ACP agent sessions alongside ZCode

## Product rules

- Existing ZCode conversations and API model Providers retain their current commands, storage, selection, and runtime. The conversation composer's **model dropdown** includes the currently enabled and runnable built-in ACP agents reported by the target Host, including Codex ACP and Claude ACP when available, alongside its existing API models. Settings continues to show all 15 catalog entries so missing or disabled adapters can be managed. ACP is a separate Agent target, never a Provider or a replacement for an existing session. The pane has no top-level ZCode/API/ACP switch or separate Agent choice buttons.
- The combined model dropdown has a compact maximum height bounded by the viewport. Its options scroll inside the menu while footer actions stay visible. Every currently available ACP target and any API model groups remain reachable by wheel, touch and keyboard, including at short window heights; opening the menu must not place its first items behind the desktop title bar. The `ModelConfigSelect` UI owns only the menu's open state, scroll position and transient pointer gesture; selection still uses the existing callback and has no new persistence or protocol state.
- Opening that dropdown or receiving a model/Agent catalog must never select a model, change the conversation target or create an ACP session. `useAvailableAcpAgents` preserves its last successful list only for the same enabled target-Host service while revalidating it on menu opening; it replaces the list on success and clears it on failure, disable or a different Host. Superseded reads cannot republish an old list. This is a renderer projection, not another Agent registry or admission owner. During pointer selection, `ModelConfigSelect` admits a mouse/touch release only for the same stable model value and pointer that received the press. If asynchronous items move a different option under the pointer, its release is cancelled and the user can explicitly press that option next. Keyboard Enter/Space and ordinary same-item mouse/touch selection remain available. No timer is used to decide that input is safe; the existing selection callbacks remain the only path to API intent or ACP selection.
- Selecting an ACP option changes the pane's local conversation target **without replacing the page or mounting a second input**. The existing `ConversationComposer` and `ChatPromptEditor` stay mounted in their original place, retain their current text, show the chosen Agent in the same model trigger, and send text through the ACP Host service. The existing conversation timeline projects that Agent's transcript, tools and permission decisions; the original ZCode rows are restored on API selection. Selecting an API model applies it to the next native submission. Available Agent options remain visible even if the API model catalog is empty or fails to load. Read-only/selection-side panes do not offer ACP switching.
- On the empty home draft, choosing an ACP Agent has the same layout effect as choosing an API model: the greeting, workspace header, suggestions and composer remain in their original centered positions. Creating an empty ACP Host session does not turn the home screen into a bottom-docked chat. Recoverable connection errors may appear above the home draft without changing its layout. Once the selected ACP session contains a user/assistant/tool entry or a permission request, the existing timeline adopts its ordinary conversation layout. An existing ZCode task keeps its conversation layout while switching targets.
- A populated ACP conversation uses the native conversation dock width, surface and vertical position even when its native ZCode task id is still null. The draft workspace selector, greeting and suggestions appear only while the _visible_ conversation is empty. The native `draftMode` still describes the ZCode submission route and must not be changed to make ACP look like a task. The ACP Host owns session identity and title; the shell receives only a read-only title projection for the existing workspace header. It never treats an ACP id as a ZCode task id or enables native task actions for it. Saved ACP conversations are selected from the existing sidebar; the composer does not add a history/new/remove menu or a separate row above the timeline. The session goal remains editable through the existing **+** action.
- A workspace may contain independent sessions for each built-in Agent. In a newly created task draft, choosing an Agent starts a fresh, empty provisional session even when that Agent has saved history. Switching API models or Agents within the same draft retains only sessions explicitly selected or created in that draft. Saved conversations are opened by clicking their sidebar row; a missing selection never falls back to the first saved session. The composer has no ACP session history button. If creation fails, keep the target selected, show the error and offer retry; never send the current draft to a different runtime.
- The pane owns a bounded, per-draft reuse list of at most two **unsubmitted provisional** ACP sessions, keyed by Agent and the exact workspace target. Switching to API or another Agent keeps these Host connections alive for a return to the same draft; a new third Agent releases the least recently selected provisional session before connecting. Returning to a retained Agent calls the Host's existing `refresh` to confirm that its connection and configuration still work before enabling prompt/config actions. A healthy connection does not run `session/new` again; an exited or unauthenticated process must not leave the controls enabled. A failed refresh shows its error and offers retry. An explicit history selection replaces and releases the Agent's retained provisional session; history uses its existing load/refresh behavior and is not an implicit draft cache. The first selection still connects before prompt admission. New Task, a changed workspace target, and pane unmount invalidate pending creates and release all pane-owned provisional connections. There is no timeout-based retention or new Host cache.
- `startDraft` increments the workspace's `draftFocusVersion`, including when its native session id was already null. The pane owns its ACP selection for that draft: on a new-task event it invalidates pending ACP creates, clears selections for all Agents, and releases only its unsubmitted provisional sessions. A late create must not override a newer draft or an explicit history click. A sidebar history click carries its exact Host id, which stays selected while the list loads; changing the native task binding also ends the previous pane selection. Persisted ACP transcripts remain Host-owned and are never removed by starting a new task.
- The target environment Host launches the selected Agent's catalog command and ACP arguments over stdio, preferring a validated managed release and otherwise using its system command. Pi requires a resolvable `pi` command or `PI_ACP_PI_COMMAND`. Antigravity reads `auth.type` from its settings file; if absent the Host writes Codeg's default `oauth-personal` without replacing an existing authentication choice. An absent executable, missing Agent authentication, or an adapter without session loading is reported in the ACP surface. No API key is copied out of ZCode Provider settings.
- Session identity is a generated ZCode ACP id plus `{ agent, workspaceIdentity?.trim() || workspacePath, workspacePath, acpSessionId }`. The path is used as ACP `cwd`; the identity is used for isolation, listing, persistence and routing. `remoteSessionId` is carried with requests for target-Host routing, but it can change after reconnect and cannot isolate durable history. Only the Agent can create or resume its ACP session.
- ACP text, tool status and permission requests have a single Host-owned snapshot and monotonic revision. The UI reads the snapshot, subscribes to notifications and resyncs on reconnect. The Host stores it under the target environment's ZCode data directory. The adapter's `session/load` reconstructs Agent context; the saved UI transcript is never sent as a new prompt.
- The shared composer keeps the existing context-capacity ring beside the model selector for every selected ACP target. A valid `session/update.usage_update` with positive `used` and `size` fills the ring and its summary. Before that exact session reports capacity, the same control shows a dashed unknown ring and the localized explanation "智能体尚未返回上下文用量", without a percentage, progress bar or invented token count. Invalid/zero reports return it to that unknown state. API visibility and rendering remain unchanged. The target Host owns the latest occupancy in its ACP session snapshot; the UI reads only the selected ACP session's occupancy, never the native/API snapshot or another Agent's history. A new session starts without inherited occupancy. ACP does not advertise an unreported cache hit rate, token breakdown or API plan quota in this panel. This occupancy is a current context-window fact, not cumulative Token spend, and never changes app usage statistics. Legacy snapshots without occupancy remain readable. Updates from a detached process generation, deleted session or another ACP session are ignored; persistence and revision notification precede desktop display, while mobile reconnect replays the latest scoped snapshot.
- While `session/new` or `session/load` is pending, the stdio adapter retains only the latest capacity metadata per native session in a bounded buffer (at most 16 native ids). It continues to discard replayed transcript/tool/permission events. After a successful response, it exposes only the matching native id's capacity on its connection port; failed initialization/load publishes none. The Host merges that optional initial fact through the existing connection-ready snapshot path. Absence of an initial report preserves the same saved session's capacity; an explicit invalid report clears it. A newer live capacity notification takes precedence over the connection's initial value, including while the Host waits for its serialized snapshot write. No adapter history-file scan, extra request, new UI store or model-name capacity estimate is introduced.
- A user prompt is admitted only while that ACP session is idle. The UI assigns a stable command id, reuses it when retrying the same text after an ambiguous RPC failure, and the Host records the user input before calling `session/prompt`; duplicate or concurrent submissions cannot execute twice. `session/cancel` stops the running turn; a late response from a previous process generation cannot change a newer turn. On process failure, mark the turn interrupted and preserve the transcript.

```text
ACP Agent usage_update(used, size) → stdio adapter → target Host ACP session owner
  → scoped snapshot write + revision → desktop continuous notification → shared composer ring
                                  └──→ mobile replayable snapshot read ──────┘
API/ZCode context window ──────────────────────────────→ same ring on API selection
```

```text
session/new or load pending → bounded capacity-only buffer (history rows discarded)
  successful native id → connection port initial capacity → Host ready snapshot/revision
  failed handshake/load → discard buffer
live capacity → same Host snapshot (newer notification wins) → existing composer ring
unknown snapshot → dashed ring + explanation; no numerical estimate
desktop: continuous revision updates; mobile: same scoped snapshot + replay repair
```

```text
conversation navigation → existing pane selection/reset (Host transcript stays authoritative)
open model menu → same-Host Agent projection + asynchronous revalidation
API/ACP catalog arrives → render options only (no selection or session/new)
pointer press value A → release value A → existing selection callback
pointer press value A → catalog moves value B under pointer → cancel release
keyboard Enter/Space → focused value → existing selection callback
desktop mouse and mobile touch use the same renderer rule; Host live/replay is unchanged
```

- Each ACP `session/request_permission` is surfaced with its Agent supplied choices. The Host waits for an explicit choice, checks session/request id, and returns `cancelled` on stop, session deletion or process loss. Never choose an approval option automatically. Unsupported client filesystem or terminal capabilities are not advertised.
- The **one existing composer instance** offers ACP turns and stop while the same conversation timeline shows tools, permissions and Agent history. ACP selection does not replace the editor or its DOM and must not navigate to another page. Its lower-left **+** opens the same menu for both ACP Agents and API models: attachments, goals, workflows, installed plugins and workspace files. Menu items must either produce an actual ACP prompt input or an explicitly routed ZCode capability; no item may silently become an uninterpreted ZCode-only marker in an external Agent turn. The ACP Host owns accepted prompts and session state, and the UI owns only unsubmitted draft content. ZCode-specific queues, branches, Provider connection settings, automations and file rewind remain on ZCode sessions. Choosing an API model restores its original native command semantics.
- Sending from the shared composer clears the submitted ACP text and attachments when the target Host first publishes the accepted `user:<commandId>` entry, without waiting for the Agent's whole turn. File/capability validation failure before admission keeps the original draft for retry. A later interrupted Agent turn keeps its accepted user row and partial output and does not restore that text. An ambiguous RPC retry uses the same command id; an admission notification or a successful idempotent reply settles that one submission. A delayed admission cannot clear text edited after submission or a newly selected target. Draft persistence for the submitted composer scope is cleared together with the accepted text, including an in-flight debounce; attachment adoption operates only on the frozen IDs.
- Durable ACP sessions with an accepted user entry appear alongside API/ZCode tasks in the existing conversation task list, sorted by their recorded entry times and isolated by workspace identity and target Host. Provisional, empty and superseded ACP sessions do not appear. The row identifies its Agent and supports selection through an ACP-specific route; it never passes its id to native task actions or CLI navigation. Choosing the row opens the original draft pane and selects that exact Host session, then projects its existing timeline and composer. The current ACP row is highlighted; choosing a native task returns the pane to API/ZCode. The list subscribes before reading Host history and merges notifications by revision so first admission, removal and reconnect remain visible. A missing remote Host shows no borrowed local sessions. Restarting the Host reloads durable rows and selecting one resumes the Agent through the existing session/load path.

### ACP conversation row actions

ACP rows use the existing leading 16px slot for the session's own Agent brand icon in project/workspace lists, worktree conversations, the chronological timeline and the pinned section. Read `session.agent` from the target Host's existing sidebar projection and reuse `AcpAgentIcon`, including its locally bundled assets and light/dark rendering. The selected composer model, title text, enabled/installed adapter list and other sessions cannot choose this icon. No new Agent cache, RPC, connection, persistence field or navigation state is introduced. Native API/ZCode rows show the model provider logo from their own task metadata and target Host's Provider Settings, reusing the model settings icon component; existing status remains a corner badge. They share the trailing pin/archive layout defined in `sidebar-conversation-rows.md`. There is no separate idle gray dot for ACP rows.

Sidebar rows do not show a visible Agent-name label such as `Codex ACP` or `Claude ACP`. The leading brand icon identifies the Agent; the row's accessible name includes its conversation title and Agent name. Keep the trailing worktree identity, showing its marker while idle and replacing it with actions on hover/focus/touch or archive confirmation; sidebar rows do not render relative time labels, as specified in `sidebar-conversation-rows.md`. This is a renderer-only presentation rule: catalog names in settings and the model selector, Host snapshots, session routing and persistence remain unchanged.

The same shared ACP row also exposes a trailing inline archive action in project, worktree, chronological and pinned lists, using the native task action button and destructive confirmation styling. Pointer hover or keyboard focus exposes the action; on devices with no hover capability the action remains available. No interaction state renders a relative time label. The idle worktree marker occupies the trailing edge and is replaced by this action group during interaction, as specified in `sidebar-conversation-rows.md`. The first inline activation enters a renderer-local confirmation state without a Host call; the second activation sends the existing scoped `IAcpService.updateRow` archive command. Archive controls do not select or resume the conversation. Escape, an outside pointer press, leaving the row with keyboard focus, selecting the row, or opening its context menu cancels that transient confirmation. The icon and confirmation reuse the same button DOM so keyboard focus survives the style/content change; before dispatch disables that button, return its keyboard focus to the owning row. Read-only rows have no inline archive action, and an in-flight row mutation disables it. A Host failure keeps the original row and reports the existing archive error; a successful Host snapshot removes the archived row and clears its pin through the existing owner. The right-click archive entry shares that same command path. The row owns transient confirmation through its local hook, while its title/archive/worktree content is a stateless presentation component. The shared action primitive's optional button variant and size retain the native task defaults.

```text
hover/focus/no-hover → shared ACP row action
first activation → row-owned confirmation (no service call)
second activation → same scoped IAcpService.updateRow → Host durable archive + unpin
                   └─ Host failure → original projection + existing error message
desktop continuous / mobile replayable → same Host snapshot → list projection
```

Verify the absence of relative time labels, trailing worktree markers, keyboard confirmation, Escape/outside cancellation, no selection or session creation on either activation, read-only suppression, busy duplicate prevention, scoped remote identity/attachment forwarding, Host failure and successful removal only after the Host projection changes. Inspect the real desktop window by hovering only; do not archive user history during verification.

### Closing an archived conversation

After the target Host confirms that a selected ACP session is archived, its pane must stop displaying that conversation. The Host remains the sole owner of the durable archived flag; `useAcpConversation` owns only the pane's exact Agent/session selection, request guards and explicit history-open intent. It consumes accepted, scoped snapshots from the existing continuous notification or replay/list/refresh path, clears only the matching selection and invalidates its pending connection/refresh work before notifying the pane. A failed archive has no accepted snapshot and must leave the selection and conversation intact. Archiving a background session, an older selection, or a same-path session on another workspace identity must not close the current conversation. Lower revisions and stale attachment callbacks cannot close or revive it.

`SessionPane` exits ACP mode without preconnecting a replacement session. The workbench owner uses its existing close-pane action for a matching ACP binding, including its existing group-collapse semantics and persisted binding cleanup; unrelated session history and native task state are untouched. An ordinary primary pane returns to its existing API draft. The shell clears only the matching ACP title/active-row projection and pending open request, so later remounts cannot replay an archived selection. Closing a view does not delete, stop or restore the Host session.

An explicit click from the archived list may open archived history. That archived-open allowance is renderer-local selection intent, not another archived-state owner; duplicate archived snapshots must not close that deliberately opened view. A later accepted restore snapshot clears the allowance, so rearchiving it closes the view again. Normal opens and restored split bindings do not receive this allowance: if their first replay snapshot is already archived, close them. Native API primary panes retain their existing successful `archiveTask` → `removeTaskState` → draft behavior.

```text
archive command → target Host durable archived snapshot (failure keeps view)
desktop continuous / mobile replay-list-refresh → scoped revision guard
    → pane selection owner clears matching id + invalidates pending work
    → SessionPane exits ACP mode
    → workbench closes matching binding; shell clears matching open request/projection
explicit archived-row open → new selection intent → archived history may render
```

Creating a session performs ACP initialization and `session/new`; sending a prompt may invoke the provider model. Client terminal/filesystem capabilities remain unadvertised.
- Removing a session deletes the ZCode display snapshot and ends its live adapter process. It does not claim to delete Agent-owned records outside ZCode. A running turn can be stopped before the next turn; the Host waits for cancellation or closes that process before admitting a replacement.

## Ownership and event order

### Shared conversation presentation

The Host keeps assistant text segments in their actual event order: consecutive chunks for the same message append in place, while text that follows a tool starts a new segment, including adapters without a message id. Updating an earlier tool does not relocate it.
ACP tool names are untrusted display labels and use the existing generic ZCode tool layout; they never dispatch to native Read, Shell, Task or workflow renderers based on a matching name.

After the first accepted ACP input, the selected Host snapshot's entries are projected into the existing `ConversationTimeline` as display-only user, assistant and tool rows. The projection is keyed by the stable entry order and the accepted command id embedded in entry ids; it never writes to the ZCode CLI transcript or claims that ACP turns have CLI actions, file changes, token accounting or runtime duration. A session switch resets the timeline scope. A streaming assistant update replaces its existing row; a tool update replaces its existing tool row. The final running turn remains live until the Host reports idle or interrupted. The timeline continues to own virtual scrolling and its existing message, markdown, copy and tool presentation. Only the current session selector, goal, errors and permission choices remain ACP-specific controls, adjacent to that timeline; no separate transcript cards or composer are rendered.

The pane derives one visible-empty-draft condition from the selected target and Host snapshot. It drives the greeting, dock centering, composer width and draft workspace selector together. The pane reports `{workspace, native task binding, ACP title}` to the shell as a display projection; the shell only shows it when the binding still matches, and clears it on target change or pane removal. Session selection and mutation continue to use the pane's existing Host commands, from the composer menu. Event order: Host accepts prompt → publishes entries/title revision → pane projects rows and populated layout → shell projects title. Switching back to API restores the original native task title and layout. Desktop live updates and mobile replay both derive layout from the same latest Host snapshot, without a second transcript or persisted UI flag.

When a permission or error control grows at the timeline tail, a reader already following the conversation remains at the bottom. If the reader has scrolled up, the new control does not take over the scroll position. The timeline owns this behavior through the same content-height observation used for message updates; the ACP control does not scroll the page directly.

The Host records an entry timestamp when it first accepts a user input, assistant message or tool call, preserving that timestamp across updates. Older saved entries have no timestamp; their display rows suppress the time label instead of inventing historical time. Attachment names from a saved ACP input remain visible as names, with no invented ZCode attachment ref or file-read action. ACP tool status is mapped conservatively to the existing display states; when a Host turn ends without a terminal tool update, the tool shows an unconfirmed result and stops animating rather than claiming success or continuing to run. Unsupported ZCode edit, fork, feedback, rewind, share and navigation actions stay absent for ACP rows. Host session identity, revision, permission request and command admission remain unchanged.

The sidebar does not render an ACP conversation's relative last-activity time or a visible Agent-name label. In the chronological timeline, its title occupies the first row and actions and an optional trailing worktree marker occupy the second metadata row; the compact project list retains its single row. The Host's accepted entry timestamps determine creation (first entry) and last activity (last entry); streaming chunks, config changes, session refresh, and selecting a history row do not change that order. An older saved conversation with no dated entries receives one Host-owned `legacySavedAt` from its JSON file's last-write time on first load; this is only an approximate **snapshot** time for sidebar ordering, not an inferred message timestamp or exact creation time. Persist it once so later refreshes or Host restarts do not push the row to the top. When neither entry time nor file time is available, preserve the existing unknown-time sort semantics instead of inventing a date. The project and chronological task lists consume the same Host projection and selected created/updated sort, with the existing running layer. A provisional conversation stays absent from history until its first accepted input. Legacy files and older remote Host snapshots without this optional field remain readable.

The Host service alone owns the mapping, accepted input and pending permission. UI state is a draft or a projection. A snapshot write completes before the corresponding revision notification. On remote reconnection the client subscribes first and reads the latest snapshot, applying only increasing revisions; the same contract serves continuous desktop and replayable mobile delivery. The remote workspace ServiceProvider uses the remote Host's ACP service and passes the existing `remoteSessionId`.

Agent configuration belongs to the same Host session snapshot. On `session/new` and `session/load`, replace previous options with the response from that process generation; newer Agent notifications and successful `set_config_option` responses replace the full option set, while `current_mode_update` updates the advertised mode. Host validation checks the current session's option type and allowed value before calling the adapter. Config changes are serialized per session and blocked while a prompt/stop is active, so a delayed response from a closed process cannot overwrite the new generation. Only IDs, display labels, categories, descriptions and selected values are persisted; opaque `_meta` is not copied into ZCode snapshots.

Selecting an existing ACP session calls the Host `refresh` command once for that selection lifecycle. It attaches to the existing Agent session with `session/load` if needed and projects its latest options into the same snapshot; pre-upgrade snapshots without config fields gain the current Agent catalog without requiring a new conversation. A failed resume keeps the saved conversation and shows the error for explicit recovery.
On an empty home session, a failed resume offers New Session and Dismiss actions. New Session creates another Agent session without deleting the old snapshot; Dismiss hides the error and leaves the draft untouched.

For a prompt with external content, the UI freezes the draft and resolves content to the selected target environment, then sends the typed blocks with one command id. The Host validates sizes, workspace identity, capabilities and active process generation before recording an accepted input; retries with that command id do not resend the turn. The target Agent receives text and content blocks in order. The Host snapshot records display metadata only; desktop streams live revisions while mobile replays the latest snapshot after reconnect. A failed validation or transfer leaves the draft intact. Switching Agents during an in-flight send cannot clear the new target's draft.

## Capability boundary in this implementation

- Settings-owned MCP and explicitly referenced skills follow [ACP ZCode MCP and skills](acp-zcode-mcp-skills.md). The target Host reads enabled MCP settings for `session/new`/`session/load`, checks the Agent's transport capabilities, and reports settings that need unsupported ZCode authentication or brokers. Skill references load the enabled skill body into that turn without changing the saved user text. The ACP `$` picker uses current settings, while API/ZCode sessions keep their native runtime catalog. Workflow execution uses the separate Host-owned bridge in [ACP 工作流](acp-workflows.md).

- Attachments and workspace file mentions are ACP input blocks; the Host validates files before admission and persists only display names. A goal is a Host-owned session field; a separate menu form updates it, and the next turn carries it as an additional text block. This supplies a durable objective, without implying the ZCode CLI `/goal` loop or verification lifecycle.
- ACP dynamic workflows execute the shared ZCode engine through a session-bound Host MCP bridge; the original API workflow and saved workflow launch paths remain separate. The ACP `+` menu inserts `/workflow`, and the Host expands the instruction while retaining the user's original history text. See [ACP 工作流](acp-workflows.md).
- ACP plugin provisioning and explicit references follow [ACP plugin capabilities](acp-plugin-capabilities.md). The target Host validates each plugin against the CLI loader's installed/enabled identity and live MCP inventory. The **+** menu lists only callable plugin capabilities; the selected `plugin://` reference is resolved again before prompt admission. Unsupported components remain unavailable with an actionable reason.
- Native API selection keeps its original session-owned plugin catalog and runtime reminder. ACP plugin tools run through the Agent's MCP client and existing ACP permission/tool update lifecycle. ZCode-specific hooks, custom commands and subagent runtime execution are outside this ACP capability contract; their mere presence cannot make a plugin callable.
